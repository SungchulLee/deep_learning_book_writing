# CPU와 메모리

---

---

## 2. CPU는 어떤 일꾼인가

CPU(중앙 처리 장치)는 **적은 수의 아주 똑똑한 일꾼**이다. CPU의 코어 수는 제품에 따라 다르지만, GPU의 병렬 연산 자원과 비교하면 개별 코어의 기능이 복잡하고 범용적이다. 코어 하나하나가 매우 빠르고, 분기 예측이나 비순차 실행 같은 장치를 갖추어 "다음에 무엇을 할지 모르는" 일도 잘 해낸다.

그래서 CPU는 다음에 강하다.

- 조건이 얽힌 논리, `if` 문이 많은 코드
- 순서를 지켜야 하는 계산
- 한 번씩만 일어나는 잡다한 일

CPU도 반복 계산을 빠르게 수행하며 SIMD 명령과 여러 스레드로 병렬 처리할 수 있다. 다만 **큰 배열에 같은 연산을 대량으로 적용하는 작업**에서는 GPU가 더 높은 처리량을 내는 경우가 많다. 뉴럴 넷트웍 학습에는 이런 연산이 자주 등장한다.

---

## 3. 메모리 계층

계산을 하려면 데이터가 CPU 가까이 와 있어야 한다. 그런데 빠른 메모리는 비싸고 작으며, 싼 메모리는 크고 느리다. 그래서 컴퓨터는 메모리를 **레이어**로 쌓는다.

| 계층 | 대략적인 용량 | 접근 지연의 예 | 비유 |
|---|---|---|---|
| 레지스터 | 수백 바이트 | 1 클럭 미만 | 손에 든 것 |
| L1 캐시 | 수십 KB | 약 1 ns | 책상 위 |
| L2/L3 캐시 | 수 MB | 약 10 ns | 서랍 속 |
| RAM(주기억 장치) | 수 GB ~ 수십 GB | 약 100 ns | 책장 |
| SSD | 수백 GB ~ 수 TB | 약 100 µs | 창고 |

표의 수치는 메모리 계층의 차이를 보여 주는 대략적인 예다. 실제 지연은 하드웨어와 접근 방식에 따라 달라지며, 모든 인접 계층 사이에 일정한 배수가 성립하는 것은 아니다. 일반적으로 CPU에서 멀리 있는 저장장치일수록 용량이 크고 접근 지연도 크다.

!!! note "ROM은 왜 여기 없는가"
    ROM(읽기 전용 메모리)은 컴퓨터가 켜질 때 쓰이는 펌웨어를 담는다. 딥러닝을 하는 동안에는 건드릴 일이 없으므로 이 책에서는 다루지 않는다. 딥러닝에서 중요한 레이어는 **캐시 → RAM → (GPU의) VRAM → SSD**이다.

이 표가 실무에서 뜻하는 바는 하나다. **데이터를 전송 비용이 계산 비용보다 클 때가 많다.** 뉴럴 넷트웍 학습이 느릴 때, 범인이 계산이 아니라 데이터를 나르는 일인 경우가 흔하다.

## 4. 파이썬 반복문은 왜 느린가

메모리 계층을 알면 딥러닝 코드에서 가장 먼저 배우는 규칙, 곧 "반복문 말고 배열 연산을 써라"를 이해할 수 있다.

```python
import time
import numpy as np

N = 1_000_000
data = np.random.randn(N)

# ========================================================
# 방법 1: 파이썬 반복문
# ========================================================
# 원소마다 파이썬 객체를 만들고, 형을 확인하고, 다음 원소의
# 주소를 따라가야 한다. 곱셈 자체보다 이 뒤치다꺼리가 훨씬 비싸다.
start = time.perf_counter()
total = 0.0
for x in data:
    total += x * x
loop_time = time.perf_counter() - start

# ========================================================
# 방법 2: NumPy 배열 연산
# ========================================================
# 같은 계산이 C로 짜인 반복문 하나로 내려간다. 자료가 메모리에
# 나란히 붙어 있으므로 캐시가 다음에 쓸 값을 미리 실어 온다.
start = time.perf_counter()
total_np = np.sum(data * data)
numpy_time = time.perf_counter() - start

print(f"원소 개수      : {N:,}")
print(f"파이썬 반복문  : {loop_time * 1e3:8.2f} ms")
print(f"NumPy 배열 연산: {numpy_time * 1e3:8.2f} ms")
print(f"차이           : {loop_time / numpy_time:.0f}배")
print(f"두 값이 같은가 : {abs(total - total_np) < 1e-6}")
```

**출력:**

```
원소 개수      : 1,000,000
파이썬 반복문  :   146.13 ms
NumPy 배열 연산:     0.96 ms
차이           : 152배
두 값이 같은가 : True
```

두 코드는 **같은 곱셈과 같은 덧셈**을 한다. 차이는 오로지 그 계산을 어디서, 어떤 차림으로 하느냐에 있다.

- Python 반복문은 매 반복마다 인터프리터의 처리와 원소 접근이 필요하다. 배열을 순차적으로 읽더라도 이 실행 오버헤드가 누적된다.
- 이 예제의 NumPy 배열은 값을 연속된 메모리에 저장한다. 배열 연산은 컴파일된 루프를 사용하므로 Python 반복문의 오버헤드를 줄이고 캐시와 벡터 연산을 효율적으로 활용할 수 있다.

!!! tip "이 절의 요점"
    텐서의 원소별 계산은 가능하면 배열 연산으로 표현하라. 다만 가독성이나 알고리즘의 특성 때문에 반복문이 필요한 경우도 있다.
    성능을 개선하려면 **실행 오버헤드와 데이터 접근 방식**을 함께 살펴야 한다.

## 5. 데이터가 나란히 붙어 있다는 것

같은 크기의 배열이라도 메모리에 놓인 차림에 따라 소요 시간이 달라진다.

```python
import time
import numpy as np

# 2차원 배열은 메모리에 '행 우선'으로 한 줄로 펼쳐져 담긴다.
# 즉 [0,0], [0,1], [0,2], ... 순서로 붙어 있다.
A = np.random.randn(4000, 4000)

def timed(fn, reps=3):
    fn()                                  # 캐시를 데운다
    start = time.perf_counter()
    for _ in range(reps): fn()
    return (time.perf_counter() - start) / reps

# 행을 따라 더하기: 메모리를 앞에서 뒤로 곧게 훑는다
row_time = timed(lambda: A.sum(axis=1))

# 열을 따라 더하기: 4000개씩 건너뛰며 훑는다
col_time = timed(lambda: A.sum(axis=0))

print(f"배열 크기            : {A.shape}, {A.nbytes / 1e6:.0f} MB")
print(f"행을 따라 더하기      : {row_time * 1e3:6.2f} ms  (메모리를 곧게 훑음)")
print(f"열을 따라 더하기      : {col_time * 1e3:6.2f} ms  (건너뛰며 훑음)")
print(f"두 합이 같은가        : {np.allclose(A.sum(axis=1).sum(), A.sum(axis=0).sum())}")
```

**출력:**

```
배열 크기            : (4000, 4000), 128 MB
행을 따라 더하기      :   2.23 ms  (메모리를 곧게 훑음)
열을 따라 더하기      :   2.55 ms  (건너뛰며 훑음)
두 합이 같은가        : True
```

더하는 숫자의 개수는 정확히 같은데도 소요 시간이 다르다. 건너뛰며 읽으면 캐시가 실어 온 덩이에서 값 하나만 쓰고 버리게 되기 때문이다.

이 기록의 시간 차이는 약 10%였다. NumPy의 반복 방식과 CPU 캐시, 입력의 메모리 배치가 함께 영향을 준다. 더 불규칙한 접근이 항상 일정 배율의 손해를 내는 것은 아니다. 핵심은 같은 수의 덧셈이라도 데이터 접근 방식에 따라 시간이 달라질 수 있다는 점이다.

이 성질은 뒤에서 PyTorch의 `view`, `reshape`, `contiguous`를 이해할 때 다시 나온다. 자세한 것은 [7장의 메모리 배치와 스트라이드](../../ch06/tensor_attrs/memory_layout_strides.md)에 있다.

**연습문제 1.** <span class="diff med" title="중간"></span>
위의 첫 번째 코드에서 `N`을 100배 줄이면 파이썬 반복문과 NumPy의 실행 시간 차이는 어떻게 되겠는가? 실제로 재어 보고 까닭을 말하라.

</div>

??? success "풀이"
    차이가 줄어든다. NumPy를 부르는 데에도 **고정 비용**(파이썬 함수 호출, 배열 검사)이 들기 때문이다. 원소가 적으면 이 고정 비용이 전체에서 차지하는 몫이 커져서 이득이 묻힌다.

    같은 이치가 GPU에도 그대로 적용된다. 과제가 작으면 GPU가 CPU보다 오히려 느리다. [CPU와 GPU 성능 비교](../pytorch/02_cpu_vs_gpu.md)에서 이를 직접 확인한다.

**연습문제 2.** <span class="diff med" title="중간"></span>
RAM이 SSD보다 1000배쯤 빠르다면, 학습 데이터를 매 에포크마다 SSD에서 새로 읽는 것과 한 번 읽어 RAM에 올려 두는 것의 차이는 얼마나 되겠는가?

</div>

??? success "풀이"
    데이터를 RAM에 보관하면 반복적인 SSD 읽기를 줄일 수 있다. 다만 표의 접근 지연 비율만으로 학습 시간이 몇 배 빨라질지 계산할 수는 없다. 순차 읽기 대역폭, 운영체제 캐시, 전처리와 모델 계산 시간도 영향을 준다.

    데이터가 RAM보다 크면 그럴 수 없으므로, 읽는 일과 계산하는 일을 **겹쳐서** 한다. GPU가 지금 배치를 계산하는 동안 다음 배치를 미리 읽어 두는 것이다. PyTorch `DataLoader`의 `num_workers`가 하는 일이 바로 이것이다.

**연습문제 3.** <span class="diff med" title="중간"></span>
두 번째 코드에서 `A`를 전치한 `A.T`에 대해 같은 실험을 하면 행 방향과 열 방향의 소요 시간이 뒤바뀌겠는가?

</div>

??? success "풀이"
    전치하면 행과 열에 대응하는 축과 스트라이드가 바뀐다. `A.T`는 보통 데이터를 복사하지 않는 뷰이므로 연속적으로 접근하는 방향도 바뀐다. 다만 NumPy의 축약 연산은 내부 순회 순서를 최적화할 수 있어, 측정 시간이 정확히 뒤바뀐다고 단정할 수는 없다.

    NumPy와 PyTorch 모두 이런 "값은 그대로 두고 보는 방식만 바꾸는" 연산을 즐겨 쓴다. 데이터 복사 비용을 줄일 수 있기 때문이다. 다만 그 뒤의 연산이 느려질 수 있다는 것이 이 실험의 요점이다.

## 정리하며

**다룬 것** — CPU의 성격과 메모리 계층

CPU는 복잡한 제어 흐름과 범용 계산에 강하며, 대규모 배열 연산에서는 GPU와 역할을 나눌 수 있다. 메모리 계층은 용량과 접근 지연의 차이를 이용하여 계산에 필요한 데이터를 공급한다.

여기서 딥러닝 코드의 첫 번째 규칙이 나온다. **계산을 줄이려 애쓰기 전에 데이터를 어떻게 늘어놓았는지 보라.** Python 반복문의 실행 오버헤드와 비연속적인 메모리 접근은 같은 계산량에서도 실행 시간을 늘릴 수 있다.

다음 절에서는 "같은 계산을 수백만 번" 하는 일을 위해 만들어진 장치인 GPU를 본다.

앞의 연습문제 3개로 직접 확인할 수 있다.
