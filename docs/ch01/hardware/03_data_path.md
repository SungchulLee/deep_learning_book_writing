## 2. 데이터 이동 경로

신경망을 학습시킬 때 숫자 하나가 지나는 길은 다음과 같다.

```
   SSD  ──────►  RAM  ──────►  GPU 메모리  ──────►  GPU 코어
        읽기          버스(PCIe)         내부 대역폭
      ~100 µs         ~10 GB/s          ~1000 GB/s
```

각 구간의 빠르기가 **자릿수로 다르다**는 점이 중요하다. 가장 느린 구간이 전체 속도를 정하므로, 학습이 느릴 때 어디를 고쳐야 하는지는 이 그림이 알려 준다.

### 버스란 무엇인가

**버스**(bus)는 부품들 사이에 데이터가 오가는 통로이다. CPU와 RAM 사이, CPU와 GPU 사이에 각각 통로가 있다. 딥러닝에서 특히 문제가 되는 것은 **CPU와 GPU를 잇는 통로**이며, 독립 GPU에서는 주로 **PCIe**가 이 역할을 맡는다.

PCIe의 대역폭은 세대와 선 수에 따라 다르지만 대략 초당 수 GB에서 수십 GB이다. GPU 내부의 대역폭이 초당 수백에서 수천 GB인 것과 견주면 **열 배에서 백 배쯤 좁다.**

그래서 규칙이 하나 나온다. **데이터를 GPU에 한 번 올렸으면 되도록 내리지 마라.** 학습 루프 안에서 `.cpu()`와 `.to('cuda')`를 오가는 코드는 이 좁은 통로를 매번 지나므로 느려진다.

!!! note "애플 실리콘에는 이 길목이 없다"
    애플 실리콘은 CPU와 GPU가 **하나의 메모리를 함께 쓴다**. 따라서 독립 GPU처럼 PCIe를 통해 별도 VRAM으로 옮기는 구조와 다르다. 다만 메모리 공유가 `.to('mps')`의 비용이 없다는 뜻은 아니다. 텐서 변환과 동기화 등의 비용이 남으므로 실제 실행 시간을 확인해야 한다.

## 3. 전송 비용과 계산 비용을 비교

말로만 하지 말고 재어 보자.

```python
import time
import torch

if torch.cuda.is_available():
    gpu, sync = 'cuda', torch.cuda.synchronize
elif torch.backends.mps.is_available():
    gpu, sync = 'mps', torch.mps.synchronize
else:
    gpu, sync = None, lambda: None

def timed(fn, sync_fn, reps=5):
    for _ in range(2): fn()
    sync_fn()
    start = time.perf_counter()
    for _ in range(reps): fn()
    sync_fn()
    return (time.perf_counter() - start) / reps

x = torch.randn(4096, 4096)                    # 4바이트 x 4096 x 4096 = 67 MB
print(f"자료 크기: {x.nbytes / 1e6:.0f} MB, 쓰는 GPU: {gpu}")

if gpu:
    # 1) CPU에서 GPU로 옮기는 데 걸리는 값
    t_move = timed(lambda: x.to(gpu), sync)

    # 2) 옮겨 놓은 자료로 계산 한 번 하는 데 걸리는 값
    xg = x.to(gpu)
    t_calc = timed(lambda: xg @ xg, sync)

    print(f"CPU -> GPU 옮기기 : {t_move * 1e3:7.2f} ms")
    print(f"행렬 곱 한 번      : {t_calc * 1e3:7.2f} ms")
    print(f"옮기는 값 / 계산 값: {t_move / t_calc:.2f}")
    print()
    print("이 값이 1보다 크면 자료를 나르느라 계산할 짬이 없다는 뜻이다.")
```

**출력:**

```
자료 크기: 67 MB, 쓰는 GPU: mps
CPU -> GPU 옮기기 :    3.22 ms
행렬 곱 한 번      :   48.18 ms
옮기는 값 / 계산 값: 0.07

이 값이 1보다 크면 자료를 나르느라 계산할 짬이 없다는 뜻이다.
```

이 비율이 핵심이다. **1보다 크면** 이 측정에서 전송 시간이 계산 시간보다 길다는 뜻이다. 전송 비용을 줄일 여지가 크지만, 전체 학습 시간은 전처리, 연산, 동기화가 겹치는 방식에도 영향을 받는다.

## 4. 학습이 느릴 때 어디를 보는가

GPU 사용률이 낮다면 **데이터 공급**, 작은 연산의 반복, 잦은 동기화 등을 의심할 수 있다. 데이터 이동 경로를 따라 병목 후보를 확인한다.

| 증상 | 의심할 곳 | 흔한 처방 |
|---|---|---|
| GPU 사용률이 들쭉날쭉하다 | 데이터 준비가 계산을 못 따라간다 | `DataLoader(num_workers=N)` |
| 매 배치마다 잠깐씩 멈춘다 | CPU에서 GPU로 전송 비용 | `pin_memory=True` |
| 첫 에포크만 느리다 | SSD에서 처음 읽는 값 | 운영체제가 캐시하도록 두기 |
| 내내 느리다 | 정말로 계산이 무겁다 | 배치 키우기, 혼합 정밀도 |

`num_workers`는 데이터를 읽고 다듬는 일을 여러 프로세스에 나눈다. GPU가 지금 배치를 계산하는 동안 일꾼들이 다음 배치를 미리 준비하므로 두 일이 **겹친다.**

CUDA를 사용할 때 `pin_memory=True`는 페이지 잠금 메모리에 배치를 준비하여 CPU에서 GPU로의 전송을 돕는다. 적절한 비동기 전송과 함께 사용하면 전송과 계산을 겹칠 수 있다. 효과는 데이터 크기와 실행 조건에 따라 다르며, 다른 장치 백엔드에 같은 효과를 가정해서는 안 된다.

!!! tip "먼저 재고 나서 고쳐라"
    위 표는 짐작을 돕는 것일 뿐이다. 실제로는 **어디가 느린지 먼저 재는 것**이 옳다.
    데이터를 아예 쓰지 않고 같은 배치를 되풀이해 넣어 보는 것이 가장 간단한 시험이다. 그래도 빨라지지 않는다면 병목은 데이터가 아니라 계산이다.

## 5. 그림으로 정리하면

```
     빠름                                                    느림
  ├────────┬─────────┬──────────┬───────────┬──────────────┤
  레지스터  캐시      RAM        SSD
           ~1 ns    ~100 ns    ~100 µs

  GPU 안:  코어 ── 내부 대역폭(~1000 GB/s) ── GPU 메모리
                                                  │
                                          버스(PCIe, ~10 GB/s)
                                                  │
  CPU 쪽:                                        RAM
```

딥러닝에서 되풀이해 마주치는 물음은 결국 하나다. **지금 데이터가 어디에 있는가?** 계산할 곳과 데이터가 있는 곳이 멀면 느리다.

**연습문제 1.** <span class="diff med" title="중간"></span>
위 코드의 비율이 0.07로 나왔다. 이는 무엇을 뜻하며, 이 기계에서 데이터 옮기기를 걱정해야 하는가?

</div>

??? success "연습문제 1 풀이"
    전송에 드는 시간이 계산의 7%에 지나지 않는다는 뜻이므로, 이 크기에서는 걱정할 일이 아니다.

    다만 이는 통합 메모리를 쓰는 기계에서 잰 값이다. PCIe로 이어진 독립 GPU라면 이 비율이 훨씬 커진다. 또한 계산이 가벼운 연산(원소별 덧셈 같은 것)이라면 분모가 작아지므로 비율이 커져서, 전송 비용이 지배하게 된다.

<div class="drillbox" markdown>

**연습문제 2.** <span class="diff med" title="중간"></span>
학습 루프 안에서 매 배치마다 `loss.item()`을 불러 손실을 쌓아 목록에 담고 있다. 이것이 왜 느려질 수 있는가?

</div>

??? success "연습문제 2 풀이"
    `.item()`은 GPU에 있는 값을 파이썬 숫자로 가져오는 일이므로 **GPU가 끝날 때까지 기다려야** 한다. GPU는 원래 명령을 쌓아 두고 뒤늦게 처리하는데, `.item()`이 그 흐름을 매번 끊는다.

    손실의 `detach()` 결과를 누적한 뒤 에포크가 끝날 때 한 번만 가져오면 동기화 횟수를 줄일 수 있다. 계산 그래프가 연결된 손실을 그대로 누적하면 메모리가 늘어날 수 있으므로 주의해야 한다.

<div class="drillbox" markdown>

**연습문제 3.** <span class="diff med" title="중간"></span>
`num_workers`를 CPU 코어 수보다 훨씬 크게 잡으면 어떻게 되겠는가?

</div>

??? success "연습문제 3 풀이"
    빨라지지 않고 오히려 느려질 수 있다. 프로세스가 코어보다 많으면 서로 번갈아 가며 실행되느라 문맥 교환 비용이 들고, 프로세스마다 메모리를 따로 쓰므로 RAM도 더 든다.

    적절한 값은 저장장치 속도, 전처리 비용, CPU와 메모리 자원에 따라 달라진다. 자기 기계에서 몇 개 값을 재어 보고 고르는 것이 옳다.

## 정리하며

**다룬 것** — 데이터가 SSD에서 GPU 코어까지 가는 길

데이터는 SSD에서 RAM으로, RAM에서 GPU 메모리로, 다시 GPU 코어로 옮겨진다. 구간마다 빠르기가 자릿수로 다르므로 가장 느린 구간이 전체를 정한다.

CPU와 GPU를 잇는 버스(PCIe)는 GPU 내부 대역폭보다 열 배에서 백 배 좁다. 그래서 데이터를 GPU에 올렸으면 학습이 끝날 때까지 내리지 않는 것이 좋다. 애플 실리콘처럼 메모리를 함께 쓰는 기계에서는 이 길목이 없어 사정이 다르다.

학습이 느릴 때는 데이터 준비, 장치 간 전송, 모델 연산, 동기화 중 어디에서 시간이 쓰이는지 먼저 확인한다. 데이터 공급이 병목이라면 작업자 수와 전송 방식을 조정한다.

앞의 연습문제 3개로 직접 확인할 수 있다.
