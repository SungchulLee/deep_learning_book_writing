# 자료가 지나는 길

---

## 1. 학습 목표

- 학습 자료가 SSD에서 GPU까지 가는 길을 짚기
- 버스(PCIe)가 무엇이며 왜 병목이 되는지 설명하기
- 자료를 옮기는 값과 계산하는 값을 견주어 재기
- GPU가 놀고 있을 때 무엇을 의심해야 하는지 말하기

---

## 2. 길목

신경망을 학습시킬 때 숫자 하나가 지나는 길은 다음과 같다.

```
   SSD  ──────►  RAM  ──────►  GPU 메모리  ──────►  GPU 코어
        읽기          버스(PCIe)         내부 대역폭
      ~100 µs         ~10 GB/s          ~1000 GB/s
```

각 구간의 빠르기가 **자릿수로 다르다**는 점이 중요하다. 가장 느린 구간이 전체 속도를 정하므로, 학습이 느릴 때 어디를 고쳐야 하는지는 이 그림이 알려 준다.

### 버스란 무엇인가

**버스**(bus)는 부품들 사이에 자료가 오가는 통로이다. CPU와 RAM 사이, CPU와 GPU 사이에 각각 통로가 있다. 딥러닝에서 특히 문제가 되는 것은 **CPU와 GPU를 잇는 통로**이며, 오늘날 이 자리는 대개 **PCIe**가 맡는다.

PCIe의 대역폭은 세대와 선 수에 따라 다르지만 대략 초당 수 GB에서 수십 GB이다. GPU 내부의 대역폭이 초당 수백에서 수천 GB인 것과 견주면 **열 배에서 백 배쯤 좁다.**

그래서 규칙이 하나 나온다. **자료를 GPU에 한 번 올렸으면 되도록 내리지 마라.** 학습 루프 안에서 `.cpu()`와 `.to('cuda')`를 오가는 코드는 이 좁은 통로를 매번 지나므로 느려진다.

!!! note "애플 실리콘에는 이 길목이 없다"
    애플 실리콘은 CPU와 GPU가 **하나의 메모리를 함께 쓴다**. 따라서 둘 사이에 PCIe 같은 좁은 통로가 없고, `.to('mps')`는 실제로 자료를 복사하기보다 쓰는 쪽을 바꾸는 일에 가깝다. 아래에서 이 값을 재어 보면 NVIDIA 기계보다 훨씬 싸게 나온다.

## 3. 옮기는 값과 계산하는 값을 견주기

말로만 하지 말고 재어 보자.

```python
import time
import torch

if torch.cuda.is_available():
    gpu, sync = 'cuda', torch.cuda.synchronize
elif torch.backends.mps.is_available():
    gpu, sync = 'mps', torch.mps.synchronize
else:
    gpu, sync = None, lambda: None

def timed(fn, sync_fn, reps=5):
    for _ in range(2): fn()
    sync_fn()
    start = time.perf_counter()
    for _ in range(reps): fn()
    sync_fn()
    return (time.perf_counter() - start) / reps

x = torch.randn(4096, 4096)                    # 4바이트 x 4096 x 4096 = 64 MB
print(f"자료 크기: {x.nbytes / 1e6:.0f} MB, 쓰는 GPU: {gpu}")

if gpu:
    # 1) CPU에서 GPU로 옮기는 데 걸리는 값
    t_move = timed(lambda: x.to(gpu), sync)

    # 2) 옮겨 놓은 자료로 계산 한 번 하는 데 걸리는 값
    xg = x.to(gpu)
    t_calc = timed(lambda: xg @ xg, sync)

    print(f"CPU -> GPU 옮기기 : {t_move * 1e3:7.2f} ms")
    print(f"행렬 곱 한 번      : {t_calc * 1e3:7.2f} ms")
    print(f"옮기는 값 / 계산 값: {t_move / t_calc:.2f}")
    print()
    print("이 값이 1보다 크면 자료를 나르느라 계산할 짬이 없다는 뜻이다.")
```

**출력:**

```
자료 크기: 67 MB, 쓰는 GPU: mps
CPU -> GPU 옮기기 :    3.22 ms
행렬 곱 한 번      :   48.18 ms
옮기는 값 / 계산 값: 0.07

이 값이 1보다 크면 자료를 나르느라 계산할 짬이 없다는 뜻이다.
```

이 비율이 핵심이다. **1보다 크면** 자료를 나르는 데 시간을 다 쓰고 있다는 뜻이므로, 계산을 아무리 최적화해도 소용이 없다.

## 4. 학습이 느릴 때 어디를 보는가

GPU 사용률이 낮다면 계산이 아니라 **자료 공급**이 병목이다. 길목을 따라 올라가며 짚는다.

| 증상 | 의심할 곳 | 흔한 처방 |
|---|---|---|
| GPU 사용률이 들쭉날쭉하다 | 자료 준비가 계산을 못 따라간다 | `DataLoader(num_workers=N)` |
| 매 묶음마다 잠깐씩 멈춘다 | CPU에서 GPU로 옮기는 값 | `pin_memory=True` |
| 첫 에포크만 느리다 | SSD에서 처음 읽는 값 | 운영체제가 캐시하도록 두기 |
| 내내 느리다 | 정말로 계산이 무겁다 | 묶음 키우기, 혼합 정밀도 |

`num_workers`는 자료를 읽고 다듬는 일을 여러 프로세스에 나눈다. GPU가 지금 묶음을 계산하는 동안 일꾼들이 다음 묶음을 미리 준비하므로 두 일이 **겹친다.**

`pin_memory=True`는 자료를 운영체제가 옮기지 못하도록 RAM에 못 박아 둔다. 그러면 GPU가 CPU를 거치지 않고 직접 읽어 갈 수 있어 옮기는 값이 준다.

!!! tip "먼저 재고 나서 고쳐라"
    위 표는 짐작을 돕는 것일 뿐이다. 실제로는 **어디가 느린지 먼저 재는 것**이 옳다.
    자료를 아예 쓰지 않고 같은 묶음을 되풀이해 넣어 보는 것이 가장 간단한 시험이다. 그래도 빨라지지 않는다면 병목은 자료가 아니라 계산이다.

## 5. 그림으로 정리하면

```
     빠름                                                    느림
  ├────────┬─────────┬──────────┬───────────┬──────────────┤
  레지스터  캐시      RAM        SSD
           ~1 ns    ~100 ns    ~100 µs

  GPU 안:  코어 ── 내부 대역폭(~1000 GB/s) ── GPU 메모리
                                                  │
                                          버스(PCIe, ~10 GB/s)
                                                  │
  CPU 쪽:                                        RAM
```

딥러닝에서 되풀이해 마주치는 물음은 결국 하나다. **지금 자료가 어디에 있는가?** 계산할 곳과 자료가 있는 곳이 멀면 느리다.

## 연습문제

**연습문제 1.**
위 코드의 비율이 0.06으로 나왔다고 하자. 이는 무엇을 뜻하며, 이 기계에서 자료 옮기기를 걱정해야 하는가?

??? success "연습문제 1 풀이"
    옮기는 데 드는 값이 계산의 6%에 지나지 않는다는 뜻이므로, 이 크기에서는 걱정할 일이 아니다.

    다만 이는 통합 메모리를 쓰는 기계에서 잰 값이다. PCIe로 이어진 독립 GPU라면 이 비율이 훨씬 커진다. 또한 계산이 가벼운 연산(원소별 덧셈 같은 것)이라면 분모가 작아지므로 비율이 커져서, 옮기는 값이 지배하게 된다.

---

**연습문제 2.**
학습 루프 안에서 매 묶음마다 `loss.item()`을 불러 손실을 쌓아 목록에 담고 있다. 이것이 왜 느려질 수 있는가?

??? success "연습문제 2 풀이"
    `.item()`은 GPU에 있는 값을 파이썬 숫자로 가져오는 일이므로 **GPU가 끝날 때까지 기다려야** 한다. GPU는 원래 명령을 쌓아 두고 뒤늦게 처리하는데, `.item()`이 그 흐름을 매번 끊는다.

    손실을 GPU 위의 텐서로 쌓아 두었다가 에포크가 끝날 때 한 번만 가져오면 이 멈춤을 없앨 수 있다.

---

**연습문제 3.**
`num_workers`를 CPU 코어 수보다 훨씬 크게 잡으면 어떻게 되겠는가?

??? success "연습문제 3 풀이"
    빨라지지 않고 오히려 느려질 수 있다. 프로세스가 코어보다 많으면 서로 번갈아 가며 실행되느라 문맥 교환 비용이 들고, 프로세스마다 메모리를 따로 쓰므로 RAM도 더 든다.

    보통은 코어 수 언저리에서 가장 좋고, 그 뒤로는 평평해지거나 나빠진다. 자기 기계에서 몇 개 값을 재어 보고 고르는 것이 옳다.

## 정리하며

**다룬 것** — 자료가 SSD에서 GPU 코어까지 가는 길

자료는 SSD에서 RAM으로, RAM에서 GPU 메모리로, 다시 GPU 코어로 옮겨진다. 구간마다 빠르기가 자릿수로 다르므로 가장 느린 구간이 전체를 정한다.

CPU와 GPU를 잇는 버스(PCIe)는 GPU 내부 대역폭보다 열 배에서 백 배 좁다. 그래서 자료를 GPU에 올렸으면 학습이 끝날 때까지 내리지 않는 것이 좋다. 애플 실리콘처럼 메모리를 함께 쓰는 기계에서는 이 길목이 없어 사정이 다르다.

학습이 느릴 때 가장 흔한 범인은 계산이 아니라 자료 공급이다. GPU가 놀고 있다면 `num_workers`와 `pin_memory`부터 살펴본다.

앞의 연습문제 3개로 직접 확인할 수 있다.
