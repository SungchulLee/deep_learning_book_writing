# Fashion-MNIST 분류기

두 컨볼루션 레이어를 사용하는 CNN으로 Fashion-MNIST를 학습하고 정확도와 클래스별 혼동을 살펴본다. 기록된 출력의 최종 테스트 정확도는 85.84%이다. 이 값은 지정한 구조·옵티마이저·러닝레이트 일정과 시드에서 얻은 예제 결과로 해석한다.

## 1. 코드

```python
"""
05_fashion_mnist_classifier.py
================================
Fashion-MNIST 데이터셋으로 CNN 학습시키기

같은 모델, 다른 데이터 = 다른 난이도!

난이도: 중간
예상 시간: 1~2시간

지은이: PyTorch CNN 실습
날짜: 2025년 11월
"""

import torch.nn as nn
import torch.optim as optim
import cnn_utils as utils

# =============================================================================
# 설정
# =============================================================================

cfg = utils.parse_args()
utils.set_seed(seed=cfg.seed)

FASHION_LABELS = ("T-shirt/top", "Trouser", "Pullover", "Dress", "Coat",
                  "Sandal", "Shirt", "Sneaker", "Bag", "Ankle boot")

# =============================================================================
# 데이터 적재
# =============================================================================

# MNIST를 부르던 줄에 fashion_mnist=True 하나만 더 준 것이다.
# 뒤의 코드는 한 줄도 고치지 않는다.
# - 학습 집합: 이미지 60,000장 (부류마다 6,000장)
# - 시험 집합: 이미지 10,000장 (부류마다 1,000장)
# - 이미지마다: 28x28 회색조 (채널 1개)
train_kwargs = {'batch_size': cfg.batch_size, 'shuffle': True}
test_kwargs = {'batch_size': cfg.test_batch_size, 'shuffle': False}
trainloader, testloader = utils.load_data(
    train_kwargs, test_kwargs, fashion_mnist=True
)

# =============================================================================
# 모델 준비
# =============================================================================

# utils.CNN 은 3x3 필터 32장과 64장을 쓰는 컨볼루션 레이어 둘에 완전 연결 레이어 둘을
# 얹은 것으로, ch03/mnist/04_cnn.md 의 구조와 같다. 파라메터는 모두
# 421,642개인데 그 가운데 fc1 하나가 3136 x 128 + 128 = 401,536개, 곧
# 95.2%를 차지한다.
model = utils.CNN().to(cfg.device)
loss_ftn = nn.CrossEntropyLoss()
optimizer = optim.SGD(model.parameters(), lr=cfg.lr, momentum=cfg.momentum)
scheduler = optim.lr_scheduler.StepLR(optimizer, step_size=1, gamma=cfg.gamma)

# =============================================================================
# 학습
# =============================================================================

utils.train(
    model, trainloader, loss_ftn, optimizer, scheduler,
    cfg.device, cfg.epochs, cfg.log_interval, cfg.dry_run
)

# =============================================================================
# 평가
# =============================================================================

# 시험 집합 첫 배치에서 10장을 골라 참값과 예측을 나란히 그린다. 맞으면
# 제목이 초록, 틀리면 빨강이다. 그림 창에만 뜨고 표준 출력에는 아무것도
# 남기지 않으므로, 아래 출력 블록에는 이 줄의 자취가 없다.
utils.show_batch_or_ten_images_with_label_and_predict(
    testloader, model, cfg.device, classes=FASHION_LABELS, n=10
)
# compute_accuracy 가 안에서 이미 'Test Accuracy: 8584/10000 (85.84%)' 를
# 찍고 값을 돌려준다. 바로 아래 print 는 그 돌려받은 값을 다시 찍는 것이라,
# 출력 끝에 같은 수가 두 줄 나온다. 잘못이 아니라 겹친 것이다.
test_accuracy = utils.compute_accuracy(model, testloader, cfg.device)
print(f"Test Accuracy: {test_accuracy:.2f}%")

if cfg.save_model:
    utils.save_model(model, cfg.path)


if __name__ == "__main__":
    pass
```

## 2. 논의

이 예제와 [MNIST CNN](../../ch03/mnist/04_cnn.md)의 결과는 데이터 내용뿐 아니라 옵티마이저·학습 기간·드롭아웃 설정이 다르다. 따라서 99.21%와 85.84%의 차이를 데이터셋만의 효과나 해당 구조의 성능 한계로 설명할 수 없다. Fashion-MNIST의 유사한 윤곽을 가진 클래스가 어려울 수 있다는 가설은 실제 혼동 표본과 통제된 비교로 확인해야 한다.

### 2.1 어느 클래스에서 잃는가

기록된 모델의 테스트셋 10000장에 대해 클래스별 재현율과 혼동 행렬을 계산한 예가 아래에 있다. 데이터셋 간 정확도 차이를 클래스에 배분한 값이 아니라 이 Fashion-MNIST 모델 자체의 오류 분포이다.

```
Shirt          : 54.90%
Pullover       : 74.00%
T-shirt/top    : 82.70%
Coat           : 82.80%
Dress          : 87.80%
Sneaker        : 93.80%
Sandal         : 94.00%
Ankle boot     : 95.00%
Bag            : 96.40%
Trouser        : 97.00%
```

가장 나쁜 넷이 정확히 소매 달린 윗옷 넷 — 셔츠, 풀오버, 티셔츠/윗옷, 코트 — 이고, 나머지 여섯 클래스는 모두 87.80% 위에 있다. 셔츠는 54.90%로 절반을 겨우 넘기는데, 틀린 451건 가운데 400건(88.7%)이 나머지 윗옷 셋으로 간다. 티셔츠로 185건, 코트로 123건, 풀오버로 92건이다.

티셔츠↔셔츠와 풀오버↔코트 같은 쌍의 혼동이 큰 것은 비슷한 윤곽을 구별하기 어렵다는 가설과 일치한다. 윗옷 네 클래스 사이의 오류는 기록된 전체 오류 1416건 중 878건이다. 다만 혼동 횟수만으로 낮은 해상도가 원인이라고 입증되지는 않는다. 원본을 단순히 확대해도 사라진 세부 정보가 복원되지는 않으며, 구조·학습 설정과 어그멘테이션의 변경 효과는 따로 검증해야 한다.

### 2.2 학습은 어디서 멈추는가

출력 블록은 에포크마다 요약 한 줄을 남긴다. 그것만 모으면 학습이 언제 끝났는지 보인다.

초반의 정확도 상승이 크고 후반에는 학습 정확도가 좁은 범위에서 변동한다. StepLR(step_size=1,gamma=0.7)이 에포크마다 러닝레이트를 줄이므로 14번째 에포크에 사용하는 값은 다음과 같다.

$$0.01 \times 0.7^{13} = 9.69 \times 10^{-5}$$

처음의 약 1/103인 러닝레이트는 갱신을 작게 만드는 요인이다. 그러나 러닝레이트가 작다는 사실과 정확도의 정체만으로 정체의 유일한 원인을 확인할 수는 없다. 느린 감쇠·고정 러닝레이트 등의 조건을 비교하고 평가 모드의 학습 로스, 검증 성능과 그래디언트도 살펴야 한다.

### 2.3 통제된 비교라고 말할 수 있는가

공통 로딩 함수를 사용하면 데이터셋 교체가 쉽다. 그러나 fashion_mnist 옵션만 바꿀 수 있다는 코드 재사용성과, 현재 문서에 실린 서로 다른 실험 결과의 공정성은 별개이다.

MNIST 예제는 Adam으로 10에포크 학습하고 이 예제는 모멘텀 SGD와 StepLR로 14에포크 학습하며 드롭아웃 위치도 다르다. 데이터셋 효과를 비교하려면 같은 구조와 평가 절차, 명시한 조율 예산으로 비교한다. 같은 시드 번호만으로 실행 환경 전반의 동일한 난수 경로가 보장되지는 않으므로 초기 상태와 분할·데이터 순서를 함께 통제한다.

    Trouser        : 97.00%

    가장 어려운 세 클래스는 **셔츠(54.90%), 풀오버(74.00%), 티셔츠/윗옷(82.70%)**이다. 코트가 82.80%로 티셔츠에 0.10%p 차이로 바짝 붙어 넷째이므로, 사실상 "가장 어려운 넷"이 소매 달린 윗옷 넷과 정확히 겹친다고 읽는 편이 낫다. 나머지 여섯 클래스(원피스, 운동화, 샌들, 앵클부츠, 가방, 바지)는 모두 87.80% 위에 있다.

    셔츠의 오류가 다른 윗옷 클래스로 집중되어 있다는 것은 윤곽과 세부 피처의 유사성이라는 가설을 뒷받침하는 관찰이다. 실제 구별 정보가 얼마나 남아 있고 모델이 무엇을 사용했는지는 오분류 이미지와 추가 분석이 필요하다. 바지나 가방의 높은 재현율도 실루엣 하나의 효과로 단정하지 않는다.

    표의 순위는 한 실행의 결과이다. 0.10%포인트 같은 작은 차이뿐 아니라 큰 순위의 안정성도 반복 실행으로 확인해야 한다. 학습 시드 변동과 유한한 테스트 표본의 불확실성은 서로 다른 요인이다.

**연습문제 3.** <span class="diff med" title="중간"></span>
난이도가 다른데도 이 모델은 MNIST와 Fashion-MNIST에 같은 구조를 쓴다. MNIST 쪽 구조는 그대로 두면서 Fashion-MNIST의 정확도를 높일 만한 구조 변경 두 가지를 제안하고, 각각이 파라메터 수를 얼마나 바꾸는지까지 셈하여 밝혀라.

</div>

??? success "연습문제 3 풀이"
    먼저 지금 모델의 파라메터를 레이어마다 갈라 두면 두 제안의 값어치를 견줄 자가 생긴다.

    ```
    conv1      320       1 x 32 x 3 x 3 + 32
    conv2   18,496      32 x 64 x 3 x 3 + 64
    fc1    401,536    3136 x 128 + 128
    fc2      1,290     128 x 10 + 10
    ----------------
    합계   421,642     이 가운데 fc1 하나가 95.2%
    ```

    파라메터의 거의 전부가 완전 연결 레이어 하나에 몰려 있다는 것이 아래 두 제안의 값을 갈라 놓는다.

    1. **셋째 컨볼루션 블록 추가**: 64→128의 3×3 컨볼루션과 추가 풀링으로 7×7을 3×3으로 줄인다는 구체적 설계라면, conv3는 73856개이고 새 fc1은 1152×128+128=147584개이다. 전체는 241546개로 줄 수 있다. 공간 해상도 감소와 깊이 증가가 성능에 미치는 영향은 별도로 검증해야 한다.
    2. **완전 연결 레이어 확장**: 은닉 차원을 128에서 256으로 늘리면 fc1은 803072개, fc2는 2570개가 되어 전체 824458개이다. 파라메터 수의 증가만으로 정확도 향상이나 과적합 위험의 상대 순위를 확정하지 않는다.

    두 설계는 풀링과 채널 수를 함께 정한 구체적 예이다. 원래 클래스와 같은 이름만으로 이 파라메터 수가 자동으로 얻어지는 것은 아니다.

    두 제안은 비교 후보이다. 같은 검증 분할과 예산에서 학습한 뒤 정확도와 연산·메모리 비용, 시드별 변동을 함께 평가한다. 평균 차이가 표준편차보다 작으면 차이가 없다는 식의 보편적인 판정 규칙은 없다. 비교 설계에 맞는 불확실성을 보고한다.

**연습문제 4.** <span class="diff hard" title="어려움"></span>
에포크마다 검증 정확도를 좇아 조기 종료를 구현하라. 검증 정확도가 세 에포크 잇달아 나아지지 않으면 학습을 멈춘다. 이 기법이 일반화에 도움이 되는 까닭을 설명하되, 검증 집합을 어디서 얻을 것인지와 멈춘 뒤 어느 웨이트를 남길 것인지를 함께 밝혀라.

</div>

??? success "연습문제 4 풀이"
    구현 자체보다 두 가지 함정을 어떻게 피하는지가 이 문제의 핵심이다.

    **함정 1 — 검증 집합을 테스트셋으로 대신하면 안 된다.** `testloader`를 보고 멈출 때를 고르면 테스트셋이 하이퍼파라미터(몇 에포크를 돌릴 것인가)를 고르는 데 쓰인 계산이고, 그렇게 고른 뒤 같은 집합으로 잰 85.84%는 더 이상 처음 보는 데이터의 값이 아니다. 검증 집합은 **학습셋에서** 떼어 내야 한다.

    **함정 2 — 멈춘 자리의 웨이트는 가장 좋았던 웨이트가 아니다.** 인내(patience)가 3이면 최고점을 지나고 세 에포크를 더 돌린 뒤에 멈춘다. 적어 두지 않으면 최고점의 웨이트는 그 세 에포크 동안 덮어써져 사라진다.

    ```python
    import copy
    import torch
    from torch.utils.data import random_split, DataLoader

    # 아래는 모델과 최적화기를 갓 만든 자리에서 돌린다는 전제다. 위에서
    # 14세대를 이미 돌린 model 을 그대로 쓰면 학습 이력이 섞인다.
    model = utils.CNN().to(cfg.device)
    optimizer = optim.SGD(model.parameters(), lr=cfg.lr, momentum=cfg.momentum)
    scheduler = optim.lr_scheduler.StepLR(optimizer, step_size=1, gamma=cfg.gamma)

    # 함정 1: 검증 집합은 학습 6만 장에서 떼어 낸다 (54,000 / 6,000)
    g = torch.Generator().manual_seed(cfg.seed)
    tr_set, val_set = random_split(trainloader.dataset, [54000, 6000], generator=g)
    tr_loader = DataLoader(tr_set, batch_size=cfg.batch_size, shuffle=True)
    val_loader = DataLoader(val_set, batch_size=cfg.test_batch_size, shuffle=False)

    best_acc = 0.0
    best_state = copy.deepcopy(model.state_dict())
    patience, patience_counter = 3, 0

    for epoch in range(cfg.epochs):
        # 한 세대 학습
        model.train()
        for data, target in tr_loader:
            data, target = data.to(cfg.device), target.to(cfg.device)
            optimizer.zero_grad()
            output = model(data)
            loss = loss_ftn(output, target)
            loss.backward()
            optimizer.step()

        # 검증 집합으로 평가한다 (시험 집합이 아니다). compute_accuracy 는
        # 어느 적재기를 주든 'Test Accuracy:' 라고 찍으니 화면에 속지 말 것.
        val_acc = utils.compute_accuracy(model, val_loader, cfg.device)

        if val_acc > best_acc:
            best_acc = val_acc
            best_state = copy.deepcopy(model.state_dict())   # 함정 2: 적어 둔다
            patience_counter = 0
        else:
            patience_counter += 1
            if patience_counter >= patience:
                print(f"Early stopping at epoch {epoch + 1}")
                break

        scheduler.step()

    # 함정 2: 멈춘 자리가 아니라 가장 좋았던 자리로 되돌려 놓는다
    model.load_state_dict(best_state)
    print(f"Best validation accuracy: {best_acc:.2f}%")
    ```

    조기 종료는 검증 성능으로 학습 기간을 선택하는 정규화 방법이다. 정체나 하락은 잡음과 최적화 상태에도 영향을 받으므로 정확히 어느 시점부터 외우기 시작했는지 알게 해 주는 방법은 아니다. 최적 검증 상태를 복원한 뒤 선택에 쓰지 않은 테스트셋에서 평가한다.

    현재 출력의 학습 정확도만으로 별도 검증셋에서 조기 종료가 언제 발동할지는 알 수 없다. 검증 정확도가 이전 최고점을 갱신하지 않으면 감소하지 않아도 patience 조건을 만족할 수 있다. 러닝레이트 일정과 patience를 함께 정하고 의도적으로 과적합을 발생시켜야만 기법을 평가할 수 있다고 가정하지 않는다.
