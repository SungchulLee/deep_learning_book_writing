# 바깥 줄 세워 합치기

자료가 기억에 담기지 않을 만큼 크면 기억 안에서 도는 여느 줄 세우기 알고리즘을 그대로 쓸 수 없다. **바깥 줄 세워 합치기**는 자료를 기억 크기만 한 토막으로 쪼개고, 토막마다 안에서 줄 세운 뒤, 줄 세운 토막들을 원반 들고남으로 합쳐 이 문제를 푼다. 데이터베이스의 `ORDER BY`, 줄 세워 합치기 맞이음, 그리고 큰 두루마리를 차례대로 닿아야 하는 온갖 일의 밑에서 일하는 것이 바로 이것이다.

## 속뜻

책상에 한 번에 100장만 놓을 수 있는데 딱지 10,000장을 줄 세워야 한다고 하자. 이렇게 할 것이다.

1. 100장을 집어 줄 세운 뒤, 줄 세운 무더기를 바닥에 놓는다.
2. 무더기 100개가 다 줄 설 때까지 되풀이한다.
3. 무더기를 합친다. 무더기마다 맨 위 딱지를 보고 가장 작은 것을 골라 내놓는 자리에 놓는다.

바깥 줄 세워 합치기는 꼭 이 꾀를 따르며, "딱지"를 원반 쪽으로, "책상"을 기억 버퍼로 바꾼 것뿐이다.

## 알고리즘

### 첫째 단계 -- 토막 짓기

자료를 한 번에 $M$쪽씩 기억에 읽어 들여, 잘 듣는 기억 안 알고리즘(보기로 빠른 줄 세우기)으로 줄 세운 다음, 줄 세운 **토막**을 원반에 되쓴다.

두루마리가 $b$쪽이고 기억이 $M$쪽이면 이렇게 해서

$$
\left\lceil \frac{b}{M} \right\rceil
$$

개의 첫 줄 세운 토막이 생기고, 토막마다 길이가 $M$쪽이다(마지막 것만 짧을 수 있다).

### 둘째 단계 -- 여러 갈래 합치기

내놓기에 한 쪽을 남기고 $(M - 1)$갈래 합치기로 줄 세운 토막을 합친다.

1. 토막을 모두(한 번에 많아야 $M - 1$개) 열고, 토막마다 첫 쪽을 기억에 읽는다.
2. 들임 쪽을 통틀어 가장 작은 낱을 골라 내놓기 쪽에 쓰기를 되풀이한다.
3. 들임 쪽 하나가 바닥나면 그 토막에서 다음 쪽을 읽는다.
4. 내놓기 쪽이 차면 원반으로 흘려보낸다.

토막의 수가 $M - 1$을 넘으면 합치기 오감이 여러 번 있어야 한다.

### 오감의 수

토막 짓기까지 아우른 온 오감의 수는 다음과 같다.

$$
1 + \left\lceil \log_{M-1}\!\left\lceil \frac{b}{M} \right\rceil \right\rceil
$$

- 0번째 오감(토막 짓기)이 토막 $\lceil b/M \rceil$개를 만든다.
- 뒤따르는 합치기 오감마다 토막의 수를 $M - 1$배만큼 줄인다.
- 줄 세운 토막이 하나만 남으면 합치기를 멈춘다.

### 들고남 비용

오감마다 모든 쪽을 한 번 읽고 한 번 쓰므로 온 들고남 비용은 다음과 같다.

$$
2 \, b \cdot \left(1 + \left\lceil \log_{M-1}\!\left\lceil \frac{b}{M} \right\rceil \right\rceil\right)
$$

2가 붙은 것은 오감마다 쪽을 한 번 읽고 한 번 쓰기 때문이다. 마지막 오감의 마지막 쓰기는 이어받는 다룸꾼(보기로 합치기 맞이음)에 곧바로 흘려보낼 때가 있어 들고남 $b$번을 아끼기도 한다.

??? example "손에 잡히는 보기"
    $b = 10{,}000$쪽, $M = 100$쪽이라 하자.

    - **오감 0**: 줄 세운 토막 $\lceil 10{,}000 / 100 \rceil = 100$개를 만든다. 비용 $2 \times 10{,}000 = 20{,}000$번.
    - **오감 1**: 99갈래 합치기로 토막 100개를 $\lceil 100/99 \rceil = 2$개로 합친다. 비용 $20{,}000$번.
    - **오감 2**: 토막 2개를 1개로 합친다. 비용 $20{,}000$번.
    - **모두**: $3 \times 20{,}000 = 60{,}000$번.

    꼴로 셈하면 $2 \times 10{,}000 \times (1 + \lceil \log_{99}(100) \rceil) = 2 \times 10{,}000 \times 3 = 60{,}000$번이다.

## 갈음 줄 세우기(토막 짓기 다듬기)

**앞선 줄**(가장 작은 것이 위로 오는 더미)을 쓰면 첫 토막을 더 길게 지을 수 있다.

1. 기억을 $M$쪽으로 채우고 가장 작은 것이 위로 오는 더미를 쌓는다.
2. 가장 작은 낱을 빼내어 지금 토막에 쓴다.
3. 들임에서 다음 낱을 읽는다. 그것이 마지막으로 내놓은 것보다 크거나 같으면 더미에 넣고, 아니면 다음 토막 몫으로 매겨 둔다.
4. 지금 토막에 쓸 낱이 더미에서 바닥나면 새 토막을 연다.

들임이 아무렇게나 놓였다고 할 때 이렇게 하면 토막이 고르게 $2M$ 길이로 나와, 첫 토막의 수가 반으로 줄고 합치기 오감 하나를 없앨 수도 있다.

!!! tip "갈음 줄 세우기가 이로울 때"
    들임이 거의 줄 서 있으면 갈음 줄 세우기가 $2M$보다 훨씬 긴 토막을 지을 수 있고, 때로는 두루마리 전체가 토막 하나에 들어가 합치기 단계가 아예 사라진다.

## 덩이 들고남 다듬기

합치는 동안 토막마다 한 쪽씩 읽는 대신 잇닿은 $B$쪽씩 읽는다. 더 큰 차례 읽기를 걸어 아무렇게나 닿는 들고남을 줄인다.

- 쓸 수 있는 합치기 갈래: $\lfloor (M - B) / B \rfloor = \lfloor M/B \rfloor - 1$
- $B$이 크면 오감마다 갈래가 줄지만 갈래마다의 들고남은 빨라진다.

가장 나은 덩이 크기는 합치기 갈래 수와 차례 읽기의 빠르기를 저울질해 정한다.

## 짜보기

```python
"""
바깥 줄 세워 합치기 -- 원반 바탕 줄 세우기 흉내내기.

기억 안 목록으로 원반 쪽을 흉내내며 두 단계 바깥 줄 세워 합치기
알고리즘을 보인다.
"""

import heapq


# === 바깥 줄 세워 합치기 ====================================================

def external_sort_merge(data: list[int], memory_pages: int,
                        page_size: int) -> list[int]:
    """옹근수 목록에 바깥 줄 세워 합치기를 흉내낸다.

    Args:
        data: 줄 세우지 않은 들임 자료.
        memory_pages: 기억에 담기는 쪽의 수(M).
        page_size: 쪽마다 담는 낱의 수(B).

    Returns:
        줄 세운 옹근수 목록.
    """
    memory_size = memory_pages * page_size

    # --- 첫째 단계: 토막 짓기 ---
    runs: list[list[int]] = []
    for start in range(0, len(data), memory_size):
        chunk = data[start:start + memory_size]
        chunk.sort()
        runs.append(chunk)

    # --- 둘째 단계: 여러 갈래 합치기 ---
    fan_in = memory_pages - 1  # 내놓기에 한 쪽을 남긴다
    while len(runs) > 1:
        new_runs: list[list[int]] = []
        for i in range(0, len(runs), fan_in):
            group = runs[i:i + fan_in]
            merged = list(heapq.merge(*group))
            new_runs.append(merged)
        runs = new_runs

    return runs[0] if runs else []


# === 셈속 ===================================================================

def compute_passes(num_pages: int, memory_pages: int) -> int:
    """바깥 줄 세워 합치기의 온 오감 수를 셈한다."""
    import math
    if num_pages <= memory_pages:
        return 1
    initial_runs = math.ceil(num_pages / memory_pages)
    merge_passes = math.ceil(math.log(initial_runs) / math.log(memory_pages - 1))
    return 1 + merge_passes


def compute_io_cost(num_pages: int, memory_pages: int) -> int:
    """바깥 줄 세워 합치기의 온 들고남 비용(읽기 + 쓰기)을 셈한다."""
    passes = compute_passes(num_pages, memory_pages)
    return 2 * num_pages * passes


# === 메인 ===================================================================

if __name__ == "__main__":
    import random

    # 흉내내기 값 차림
    random.seed(42)
    n_records = 10000
    page_size = 100
    memory_pages = 10
    data = random.sample(range(n_records * 10), n_records)

    print(f"낱: {n_records}개")
    print(f"쪽 크기: 낱 {page_size}개")
    print(f"기억: {memory_pages}쪽 (낱 {memory_pages * page_size}개)")

    num_pages = (n_records + page_size - 1) // page_size
    passes = compute_passes(num_pages, memory_pages)
    io_cost = compute_io_cost(num_pages, memory_pages)
    print(f"쪽: {num_pages}개")
    print(f"오감: {passes}번")
    print(f"들고남 비용: 쪽 옮김 {io_cost}번")

    sorted_data = external_sort_merge(data, memory_pages, page_size)
    assert sorted_data == sorted(data), "줄 세우기 살핌에 걸림"
    print(f"줄 세우기 살핌 마침: 앞의 10개 = {sorted_data[:10]}")
```

## 익힘 문제

**익힘 1.**
두루마리가 1000쪽이고 버퍼 못이 5쪽이다. 첫 오감에서 줄 세운 토막이 몇 개 생기고 합치기 오감이 몇 번 있어야 하는가?

??? success "익힘 1 풀이"
    첫 오감에서는 한 번에 5쪽을 읽어 기억에서 줄 세운 뒤 되쓴다. 줄 세운 토막의 수는 $\lceil 1000 / 5 \rceil = 200$개다. 합치기 오감마다 버퍼 $B - 1 = 4$쪽을 들임에(토막마다 한 쪽), 1쪽을 내놓기에 써서 한 번에 토막 4개를 합친다. 합치기 오감의 수는 $\lceil \log_4(200) \rceil = \lceil 3.82 \rceil = 4$번이다. 온 오감은 $1 + 4 = 5$번이다. 온 들고남은 $2 \times 1000 \times 5 = 10{,}000$번의 쪽 읽기와 쓰기다. $\square$

**익힘 2.**
첫 토막을 더 길게 짓는 갈음 줄 세우기 다듬기를 밝혀라. 언제 이로운가?

??? success "익힘 2 풀이"
    갈음 줄 세우기는 크기가 $M$(버퍼 쪽 수)인 앞선 줄(가장 작은 것이 위로 오는 더미)을 쓴다. 자료를 읽으며 낱을 더미에 넣고, 가장 작은 것을 지금 토막에 내놓는다. 새 낱을 읽었을 때 마지막으로 내놓은 것보다 크거나 같으면 지금 토막에 붙고, 작으면 다음 토막 몫으로 매겨져 더미에 남는다. 아무렇게나 놓인 들임에 대해 고르게 크기 $2M$(버퍼의 두 곱절)인 첫 토막이 나온다. 거의 줄 선 들임이면 토막이 훨씬 길어질 수 있다(두루마리 전체까지도). 이렇게 첫 토막의 수가 줄어 합치기 오감을 아낀다. 자료에 어느 만큼 차례가 배어 있을 때, 그리고 두루마리 크기에 견주어 $M$이 작을 때 가장 이로운데, 긴 토막이 $\lceil \log_{B-1}(\text{토막 수}) \rceil$을 줄이기 때문이다. $\square$

**익힘 3.**
버퍼가 $B$쪽일 때 $N$쪽짜리 두루마리에 바깥 줄 세워 합치기를 하면 들고남이 $O(N \log_{B-1}(N/B))$번 든다는 것을 밝혀라.

??? success "익힘 3 풀이"
    줄 세우기 단계는 줄 세운 토막 $\lceil N/B \rceil$개를 만들며 쪽 읽기 $N$번과 쪽 쓰기 $N$번이 든다. 합치기 단계마다 $N$쪽을 모두 읽고 $N$쪽을 쓰며 토막의 수를 $B - 1$배만큼 줄인다. 합치기 오감의 수는 $\lceil \log_{B-1}(N/B) \rceil$이다. 온 들고남은 $2N \times (1 + \lceil \log_{B-1}(N/B) \rceil) = O(N \log_{B-1}(N/B))$이다. $\log_{B-1}$ 몫은 합치기 나무의 갈래 폭을 드러낸다. 합치기가 넓을수록(버퍼 쪽이 많을수록) 오감이 줄어든다. $B = 101$(100갈래 합치기)이고 $N = 10^6$쪽이면 오감이 $\lceil \log_{100}(10^4) \rceil = 2$번이므로 온 들고남은 $\approx 6 \times 10^6$번이다. $\square$

**익힘 4.**
겹 버퍼 쓰기가 바깥 줄 세워 합치기의 들고남 살림을 어떻게 낫게 하는지 밝혀라. 어떤 쇠 붙임새의 됨됨이를 살려 쓰는가?

??? success "익힘 4 풀이"
    겹 버퍼가 없으면 원반에서 쪽이 읽히기를 기다리는 동안 CPU가 놀고, CPU가 쪽을 다루는 동안 원반이 논다. 겹 버퍼는 들임 줄기마다 버퍼 둘을 잡는다. CPU가 버퍼 A의 자료를 다루는 동안 원반이 다음 쪽을 버퍼 B로 미리 읽어 둔다. CPU가 A을 마치면 곧바로 B로 갈아타고 원반은 A을 채우기 시작한다. 이렇게 들고남과 셈이 겹쳐 돌아, 원반과 CPU가 서로 남남으로 함께 일할 수 있는 쇠 붙임새라는 점을 살린다. 값으로는 줄기마다 버퍼 자리가 두 곱절 든다. 버퍼가 $B$쪽일 때 겹 버퍼를 쓰면 합치기 줄기를 $(B-1)/2$개만 함께 돌릴 수 있다. 들고남 늦음이 판칠 때는 이 맞바꿈이 남는 장사이고, HDD 바탕 얼개가 그렇다. 늦음이 작은 SSD에서는 얻는 것이 적다. $\square$

**익힘 5.**
`GROUP BY` 물음에 대해 바깥 줄 세워 합치기와 바깥 해시 바탕 묶기를 견주어라. 저마다 언제 알맞은가?

??? success "익힘 5 풀이"
    **바깥 줄 세워 합치기**: 묶는 열쇠로 자료를 줄 세운 다음, 줄 선 열매를 훑으며 잇닿은 묶음을 뭉뚱그린다. 비용은 들고남 $O(N \log_{B-1}(N/B))$이다. 줄 세운 내놓기가 나온다(`ORDER BY`이 함께 있으면 이롭다). **바깥 해시 바탕 묶기**: 묶는 열쇠를 해시해 자료를 나눈 다음, 나눔마다 따로 뭉뚱그린다. 비용은 나눔이 기억에 담기면 $O(N)$이고, 나누기 오감 한 번을 더하면 $O(3N)$이다. 줄 세운 내놓기는 나오지 않는다. 줄 세우기가 나을 때는 (1) 물음이 줄 세운 내놓기도 바랄 때, (2) 묶는 열쇠의 서로 다른 값이 적을 때(줄 세우기 + 차례 훑기가 단순하고 갈무리에 잘 맞는다)다. 해시가 나을 때는 (1) 줄 세운 내놓기가 없어도 될 때, (2) 자료가 커서 들고남 오감을 줄이는 것이 중요할 때, (3) 묶음의 수가 적어 나눔마다의 해시 표가 기억에 담길 때다. 요즘 데이터베이스는 대개 `GROUP BY`에 해시를 쓰고, `ORDER BY`이 함께 적힐 때만 줄 세우기를 쓴다. $\square$
