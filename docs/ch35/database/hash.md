# 해시 색인

B 나무 색인은 범위 물음과 차례 있는 훑기에 뛰어나지만, 많은 데이터베이스 일감은 거의 **딱 맞는 찾기**로 이루어진다. 아이디가 42인 쓰는 이를 찾거나 토막표가 `abc123`인 이음을 되찾는 일이 그러하다. 해시 색인은 이 결에 맞추어 다듬어져, 열쇠마다 해시 함수로 곧바로 그 갈무리 자리를 맞대어 찾기마다 어림 $O(1)$ 들고남을 이룬다. 이 쪽은 곳간 엔진에서 해시 색인이 도는 길, 그 매임, 통째로 다시 세우지 않고 자람을 다루는 움직이는 해싱 얼개를 다룬다.

## 붙박인 해시 색인

붙박인 해시 색인은 기록을 붙박인 **두레박** $m$개로 가른다. 두레박마다 원반 쪽 하나 이상을 차지한다. 열쇠 $k$을 갈무리하거나 되찾으려면 다음을 쓴다.

$$
\text{두레박}(k) = h(k) \bmod m
$$

여기서 $h$은 열쇠를 정수로 맞대는 해시 함수다.

### 연산

| 연산 | 어림 들고남 | 가장 나쁠 때 |
|-----------|--------------|------------|
| 낱점 찾기 | $O(1)$ | $O(n/m)$ (온 열쇠가 부딪침) |
| 넣기 | $O(1)$ | $O(n/m)$ |
| 지우기 | $O(1)$ | $O(n/m)$ |
| 범위 물음 | $O(n)$ | $O(n)$ |

해시 색인의 치명적인 약점은 **범위 물음이 통째로 훑기를 바란다**는 것이다. 해시 함수가 열쇠의 차례를 무너뜨리기 때문이다. 이것이 거의 모든 관계형 데이터베이스가 B 나무 색인을 기본으로 삼는 까닭이다.

## 해시 색인과 B 나무

| 성질 | 해시 색인 | B 나무 색인 |
|----------|-----------|-------------|
| 낱점 찾기 | 어림 $O(1)$ | $O(\log_t n)$ |
| 범위 물음 | $O(n)$ -- 통째로 훑기 | $O(\log_t n + k/B)$ |
| 차례 있는 훑기 | 받쳐 주지 않음 | 절로 됨 |
| 자리 덧듦 | 적음 | 어중간 |
| 가장 나쁠 때 | 부딪침으로 $O(n)$ | $O(\log_t n)$ 보장 |

## 넘침 다루기

두레박이 쪽 용량을 넘어 차면 색인은 **넘침 사슬 잇기**를 쓴다. 덧쪽을 으뜸 두레박 쪽에 이어 붙인다. 사슬이 길어지면 됨됨이가 나빠지며, 이것이 움직이는 해싱 얼개를 불러낸다.

## 늘릴 수 있는 해싱

늘릴 수 있는 해싱은 해시 값의 앞 $d$비트(**온 세상 깊이**)로 번호를 매긴 손가락질 $2^d$개의 **목록**을 써서 온 표를 다시 해시하는 일을 비껴간다. 두레박마다 **제 깊이** $d_i \leq d$을 지닌다.

### 넘칠 때 쪼개기

두레박 $b$이 넘치면:

1. $d_b < d$이면(제 깊이가 온 세상 깊이보다 작으면):
    - 두레박 $b$을 둘로 쪼개고 $d_b$을 올린다.
    - $b$을 가리키던 목록 항목을 고친다.
2. $d_b = d$이면:
    - 목록을 곱절로 늘린다($d \leftarrow d + 1$).
    - 그런 뒤 1번처럼 두레박을 쪼갠다.

목록을 곱절로 늘리는 데 $O(2^d)$이 들지만 자료 기록은 하나도 옮기지 않는다. 손가락질만 베낀다. 두레박 쪼개기는 두레박 하나의 기록 가운데 대략 절반을 옮긴다.

### 복잡도

| 연산 | 어림 들고남 |
|-----------|--------------|
| 찾기 | $O(1)$ -- 목록 쪽 1 + 두레박 쪽 1 |
| 넣기(쪼개지 않음) | $O(1)$ |
| 넣기(쪼갬) | $O(1)$ 나눠 갚음 |
| 목록 곱절로 늘리기 | $O(2^d / B)$ 들고남 |

## 곧게 늘어나는 해싱

곧게 늘어나는 해싱은 두레박을 정해진 차례로 **하나씩** 늘려 목록을 아예 없앤다. 다음을 지닌다.

- 다음에 쪼갤 두레박을 가리키는 **쪼개기 손가락질** $p$.
- 표가 몇 번 곱절이 되었는지 좇는 **켜** $l$.

해시 함수는 $h_l(k) = k \bmod (2^l \cdot m)$과 $h_{l+1}(k) = k \bmod (2^{l+1} \cdot m)$을 번갈아 쓴다.

아무 두레박이 넘치면 (넘친 그 두레박이 아니라) 자리 $p$의 두레박을 쪼갠다.

1. 두레박 $p + 2^l \cdot m$을 만든다.
2. 두레박 $p$의 기록을 $h_{l+1}$으로 다시 해시한다.
3. $p$을 앞으로 옮긴다. $p = 2^l \cdot m$이면 $p = 0$으로 되돌리고 $l$을 올린다.

이 다스린 늘리기가 다시 해시하는 비용을 넣기마다 고르게 퍼뜨린다.

## Bitcask -- 해시로 색인한 곳간 엔진

!!! example "Bitcask (Riak)"
    Bitcask은 열쇠마다 원반 파일의 어긋남을 맞대는 **해시 표를 기억에** 지니는, 기록 얼개 곳간 엔진이다. 적기는 기록 파일에 덧붙이고, 읽기는 기억 안 손가락질을 따라 원반의 바로 그 자리로 간다.

    - **적기**: $O(1)$ -- 기록에 덧붙인다.
    - **읽기**: $O(1)$ -- 기억에서 한 번 찾고 원반에서 한 번 자리를 옮긴다.
    - **매임**: 온 열쇠가 기억에 들어가야 한다.

    적기가 잇달아 있으므로(아무 들고남이 없다) 적기 처리량이 아주 높고, 읽기는 원반에 꼭 한 번만 닿는다.

## 구현

```python
"""
늘릴 수 있는 해싱 -- 움직이는 해시 색인 보여 주기.

해시로 색인한 얼개에 기록을 넣으면서 두레박 쪼개기와 목록을
곱절로 늘리기를 보인다.
"""

# === 두레박 ===================================================================

class Bucket:
    """제 깊이를 좇는 해시 두레박."""

    def __init__(self, local_depth: int, capacity: int = 3):
        self.local_depth = local_depth
        self.capacity = capacity
        self.records: dict[int, str] = {}

    def is_full(self) -> bool:
        return len(self.records) >= self.capacity

    def insert(self, key: int, value: str) -> None:
        self.records[key] = value


# === 늘릴 수 있는 해시 표 =====================================================

class ExtendibleHashTable:
    """목록을 곱절로 늘리는 늘릴 수 있는 해시 표."""

    def __init__(self, capacity: int = 3):
        self.global_depth = 1
        self.capacity = capacity
        b0 = Bucket(1, capacity)
        b1 = Bucket(1, capacity)
        self.directory = [b0, b1]

    def _hash(self, key: int) -> int:
        return key % (2 ** self.global_depth)

    def lookup(self, key: int) -> str | None:
        idx = self._hash(key)
        bucket = self.directory[idx]
        return bucket.records.get(key)

    def insert(self, key: int, value: str) -> None:
        idx = self._hash(key)
        bucket = self.directory[idx]

        if not bucket.is_full():
            bucket.insert(key, value)
            return

        # 쪼개야 한다
        if bucket.local_depth == self.global_depth:
            # 목록을 곱절로 늘린다
            self.directory = self.directory + self.directory[:]
            self.global_depth += 1

        # 두레박을 쪼갠다
        old_depth = bucket.local_depth
        new_depth = old_depth + 1
        b0 = Bucket(new_depth, self.capacity)
        b1 = Bucket(new_depth, self.capacity)

        # 있던 기록을 다시 해시한다
        for k, v in bucket.records.items():
            if (k >> old_depth) & 1 == 0:
                b0.insert(k, v)
            else:
                b1.insert(k, v)

        # 목록 손가락질을 고친다
        for i in range(len(self.directory)):
            if self.directory[i] is bucket:
                if (i >> old_depth) & 1 == 0:
                    self.directory[i] = b0
                else:
                    self.directory[i] = b1

        # 넣기를 다시 꾀한다
        self.insert(key, value)


# === 메인 =====================================================================

if __name__ == "__main__":
    ht = ExtendibleHashTable(capacity=2)
    entries = [(2, "a"), (5, "b"), (7, "c"), (10, "d"), (15, "e"), (22, "f")]

    for key, val in entries:
        ht.insert(key, val)
        print(f"Insert ({key}, {val}) -> depth={ht.global_depth}, "
              f"buckets={len(ht.directory)}")

    # 찾기
    for key in [5, 10, 99]:
        result = ht.lookup(key)
        print(f"Lookup {key}: {result}")
```

**출력:**
```
Insert (2, a) -> depth=1, buckets=2
Insert (5, b) -> depth=1, buckets=2
Insert (7, c) -> depth=2, buckets=4
Insert (10, d) -> depth=2, buckets=4
Insert (15, e) -> depth=3, buckets=8
Insert (22, f) -> depth=3, buckets=8
Lookup 5: b
Lookup 10: d
Lookup 99: None
```

## 연습문제

**연습문제 1.**
해시 색인이 범위 물음을 받쳐 주지 못하는 까닭을 풀어라. 해시 함수의 어떤 얼개 성질이 차례 있는 닿기를 막는가?

??? success "연습문제 1 풀이"
    해시 함수는 열쇠를 두레박에 고르게, 아무렇게나 보이게 흩뿌리도록 설계된다. 값이 가까운 두 열쇠(보기로 100과 101)가 서로 얽히지 않은 두레박 자리로 간다. 이로써 차례가 무너진다. 범위 물음 `WHERE id BETWEEN 100 AND 200`은 겨눈 열쇠가 흩어져 있으므로 온 두레박을 살펴야 한다. B 나무 색인은 매긴 차례를 지키므로 범위 훑기가 아래 끝에서 시작해 위 끝까지 쪽을 죽 읽는다. 해시 색인은 $O(1)$ 낱점 찾기를 주지만 범위 훑기가 $O(n)$이다(표 통째로 훑기와 같다). 이것이 데이터베이스가 B 나무 색인을 기본으로 삼고, 일감이 오로지 딱 맞는 찾기뿐일 때에만 해시 색인을 쓰는 까닭이다. $\square$

**연습문제 2.**
늘릴 수 있는 해싱을 밝히고, 온 표를 다시 해시하지 않고 두레박 넘침을 다루는 길을 풀어라.

??? success "연습문제 2 풀이"
    늘릴 수 있는 해싱은 해시 앞가지를 두레박에 맞대는 손가락질 $2^d$개의 목록을 쓴다($d$은 온 세상 깊이). 두레박마다 제 깊이 $d_b \le d$을 지닌다. 넘칠 때: $d_b < d$이면 두레박을 둘로 쪼개고 $d_b$을 올린 뒤 걸맞은 목록 항목이 새 두레박을 가리키게 고친다. $d_b = d$이면 목록을 곱절로 늘리고($d \to d + 1$) 온 손가락질을 베낀 뒤 두레박을 쪼갠다. 종요롭게도 두레박 하나만 쪼개지고 목록 곱절 늘리기가 많아야 한 번 생긴다. 넘친 두레박의 기록 말고는 어떤 기록도 옮기지 않는다. 두레박 크기를 $B$이라 할 때 $O(B)$ 일이며, 통째로 다시 해시하는 $O(n)$과 견주어진다. 목록은 (손가락질 $2^d$개로 작아) 기억에 들어가므로 쪼갠 두레박만 원반에 들고난다. $\square$

**연습문제 3.**
어떤 해시 색인이 채움률 $\alpha$으로 곧게 더듬기를 쓴다. 찾기가 이루어질 때와 어그러질 때의 어림 더듬기 횟수를 이끌어 내어라.

??? success "연습문제 3 풀이"
    고른 해싱을 여기면 크누스의 살핌은 다음을 준다. **이루어지는** 찾기의 어림 더듬기: $\frac{1}{2}(1 + \frac{1}{1 - \alpha})$. **어그러지는** 찾기의 어림 더듬기: $\frac{1}{2}(1 + \frac{1}{(1-\alpha)^2})$. $\alpha = 0.5$이면 이루어질 때 $1.5$번, 어그러질 때 $2.5$번이다. $\alpha = 0.75$이면 $2.5$번과 $8.5$번이다. $\alpha = 0.9$이면 $5.5$번과 $50.5$번이다. $\alpha = 0.75$ 너머에서 가파르게 나빠지는 것이 해시 표를 흔히 채움률 70~75%에서 크기 바꾸는 까닭이다. 데이터베이스 해시 색인에서는 더듬기마다 원반 들고남이므로 기억 안 해시 표보다 그 비용이 한층 더 대수롭다. $\square$

**연습문제 4.**
기록이 1000개에서 1000만 개로 자라는 데이터베이스에서 붙박인 해싱, 늘릴 수 있는 해싱, 곧게 늘어나는 해싱을 견주어라. 어느 길이 자람을 가장 잘 다루는가?

??? success "연습문제 4 풀이"
    **붙박인 해싱**: 만들 때 두레박 개수를 정해 둔다. 기록이 자라면 두레박이 넘쳐 사슬이 길어진다. 끝내 통째로 다시 세워야 한다(표를 잠그는 값비싼 $O(n)$ 연산). 자라는 데이터베이스에 나쁘다. **늘릴 수 있는 해싱**: 필요할 때 목록을 곱절로 늘리지만($O(2^d)$) 한 번에 두레박 하나만 쪼개진다. 자람을 매끄럽게 다룬다. 나쁜 점: 자료 분포가 치우치면 목록이 아주 커질 수 있다($2^d$개 항목). **곧게 늘어나는 해싱**: 평균 짐이 문턱을 넘으면 두레박을 돌아가며 하나씩 쪼갠다. 목록이 필요 없고 두레박 개수가 곧게 는다. 넘침 사슬은 잠깐뿐이다(넘친 두레박이 끝내 쪼개지면 풀린다). 통째로 다시 세우기와 큰 목록을 모두 비껴가고 쪼개기마다 어림할 수 있는 $O(1)$ 나눠 갚는 비용을 지니므로, 큰 잣대 데이터베이스에서 자람을 가장 잘 다룬다. $\square$

**연습문제 5.**
(Riak이 쓰는) Bitcask은 열쇠마다 파일 어긋남을 맞대는 해시 색인을 기억에 지닌다. 평균 길이 20바이트인 열쇠 $10^8$개에 드는 자리를 살피고, 적기가 많은 일감에 잘 듣는 까닭을 따져라.

??? success "연습문제 5 풀이"
    해시 색인 항목마다 열쇠(평균 20바이트), 파일 아이디(4바이트), 어긋남(8바이트), 값 크기(4바이트), 때 도장(4바이트)을 갈무리한다. 항목마다 온통 약 40바이트다. 열쇠가 $10^8$개면 색인에 $40 \times 10^8 = 4$ GB의 RAM이 든다. 요즘 서버에서는 될 만하지만 열쇠 개수를 매어 둔다. 적기에 잘 듣는 까닭: Bitcask의 적기는 늘 살아 있는 자료 파일에 잇달아 덧붙이는 것이다. 아무 들고남도, 제자리 고치기도 없다. 이로써 원반 처리량이 가장 커진다(굳은 원반에서 잇단 적기가 아무 적기보다 100배 빠르다). 읽기는 늘 아무 들고남 한 번이다(기억 안 해시 표에서 어긋남을 찾고 그 자리로 옮긴다). 맞바꿈은 이렇다. 온 열쇠 모임이 RAM에 들어가야 하고 범위 물음을 받쳐 주지 않는다. 열쇠 개수가 매여 있고 적기 처리량이 높아야 하는 자리(이음 곳간, 캐시)에서 Bitcask은 아주 잘 듣는다. $\square$
